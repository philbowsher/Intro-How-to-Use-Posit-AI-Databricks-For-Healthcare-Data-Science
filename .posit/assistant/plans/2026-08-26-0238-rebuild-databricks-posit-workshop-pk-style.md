## Key adaptation notes (Python/Databricks vs R/PK differs from the source pattern)

1. **No "pick your dataset" step** — single dataset confirmed, so PK's Doc-1 "if time permits, switch dataset and redo" stretch pattern doesn't translate. Substitute a different stretch activity (see Workflow slides below).
2. **Package risk profile is different.** PK's gotcha was a CRAN source-compile failure needing R-internals symbols absent from a pinned R version. This is a pip/Python stack: the realistic equivalent risks are (a) `databricks-sql-connector` bringing in `pyarrow`/`thrift` native wheels that may lack prebuilt wheels for very new Python (this repo pins `>=3.14.2`, which is bleeding-edge and a real risk for missing wheels), and (b) Quarto's Python discovery needing `QUARTO_PYTHON` pointed at the right venv. `check_packages`-equivalent should be a Python script that checks/installs against a **pinned requirements list with exact versions** (closest available equivalent to a dated snapshot, since pip has no MRAN-style dated mirror) and gives per-package pass/fail diagnostics, not a wall of pip noise.
3. **No R-console "source the whole script" equivalent needed** — Python scripts run via `python check_packages.py` from Positron's terminal or console.
4. **Connection boilerplate duplication is the real infrastructure smell here.** Right now every one of the 4 solutions + streamlit_app re-pastes the same connect+query+schema code. The PK pattern's "one script, one time" principle maps onto: a single `databricks_setup.py` (or `.env`-driven helper module) that opens the connection, runs the VALUES-clause query once, and writes a local Parquet/CSV cache — so each of the four working documents loads from that cache/module instead of re-authenticating live. This mirrors `generate_pk_datasets.R` writing `pk_data`/CSV once.
5. **Scaffold script must create all four working docs deterministically**, matching `create_workshop_docs.R`: extend the existing `new_analysis.qmd`-style template approach to also produce blank `Dashboard.qmd`, `app.py`, `app_streamlit.py` with section headers/placeholders in place — replacing the README's current "ask Assistant to build it from a blank file" instruction with "ask Assistant to fill in each section of the pre-scaffolded file."
6. **Validation-equivalent**: Python analog of `pointblank` is `pandera` (or plain Polars assertions) — a standalone `validation/validate_data.py` checking no negative `days_waiting`, valid `priority` values, no null hospital/specialty, etc. Optional/skippable slide, same as PK.
7. **Dry run limitation to flag explicitly to the user**: I do not have live Databricks credentials in this environment. I can fully dry-run everything downstream of the connection (the synthetic VALUES data, the scaffolded documents, the package-check script logic, rendering Quarto docs against a local cached copy of the data, the Shiny/Streamlit apps against that cache). I **cannot** verify the actual `sql.connect()` round-trip, real warehouse cold-start behavior, or real PAT auth failure modes. This should be written into the skill file as a documented limitation/TODO for the user (or a future session with real credentials) rather than silently assumed to work.
8. **Pacing bottleneck candidate**: unlike PK (where Doc 3, population PK modeling, was the clear bottleneck), here the likely bottleneck is **Workflow 3 (Shiny reactive app)** — reactive programming (`@reactive.calc`, `@render.ui`) is the first genuinely new *programming model* attendees hit, vs. Workflows 1/2/4 which are mostly "describe a chart, get a chart." A secondary/compounding bottleneck candidate is **Phase 1 connectivity** (Databricks signup + PAT + warehouse cold start) purely from elapsed-wall-clock risk, not conceptual difficulty. Plan: budget extra explicit time for Workflow 3 on its slide, and build a small helper (e.g. a `reactive_filter_helper.py` pattern or at minimum a fully-worked reference snippet for the trickiest reactive filter chain) so live prompting for Workflow 3 doesn't have to get the reactive wiring right from scratch. Will confirm this read with the user before finalizing slide time budgets.

### Hard-won lesson to carry over exactly: no placeholder code chunks in scaffolded docs
